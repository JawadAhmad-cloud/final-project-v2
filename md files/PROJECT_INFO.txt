SECTION 1: PROJECT OVERVIEW
================================================================================

PROJECT DESCRIPTION:
ShopFlow is a comprehensive, production-ready e-commerce platform that enables multiple 
sellers to manage their own shops while customers browse products, place orders, and 
leave reviews. The platform supports three types of users: regular customers (users), 
shop owners (sellers), and administrators (admins).

PRIMARY OBJECTIVES:
1. Develop a fully functional e-commerce platform supporting multiple sellers
2. Implement secure user authentication and role-based access control
3. Create an efficient inventory management system
4. Enable seamless payment processing through dummy payment gateway
5. Provide a user-friendly interface for customers and sellers
6. Implement order tracking and status management with real-time notifications
7. Support product reviews and ratings
8. Provide seller analytics and sales tracking
9. Implement admin dashboard for platform management

PROJECT SCOPE:
- Multi-seller marketplace with independent shop management
- User authentication with email verification via OTP
- Product inventory management with stock tracking
- Order lifecycle management (creation, payment, shipping, delivery)
- Payment processing with commission management
- Real-time order notifications via Socket.io
- Admin dashboard for user and order management
- Product review and rating system
- Seller analytics and revenue tracking
- Shipping integration with TCS (simulated)

SECTION 5: DATABASE DESIGN & MODELS
================================================================================

DATABASE: MONGODB

User Model (User Collection):
Fields:
- _id: MongoDB ObjectId (auto-generated)
- username: String (required, unique, 3+ chars)
- email: String (required, unique, valid email)
- password: String (required, hashed with bcryptjs, min 6 chars)
- firstname: String (optional)
- lastname: String (optional)
- phonenumber: String (validated 10-15 digits)
- dob: Date (optional)
- role: String enum (user, seller, admin) - default: user
- addresses: Array of objects with:
  * street, city, postalcode, country
  * isdefault: Boolean
- favourite: ObjectId reference to Favourite model
- cart: ObjectId reference to Cart model
- orders: Array of ObjectId references to Order model
- shop: ObjectId reference to Shop model (if seller)
- isactive: Boolean (default: true)
- isverified: Boolean (default: false)
- otp: String (6-digit code)
- otpexpiry: Date (expires in 10 minutes)
- otpAttempts: Number (tracks failed OTP attempts)
- currency: String (user's preferred currency)
- language: String (user's preferred language)
- createdAt: Date (auto timestamp)
- updatedAt: Date (auto timestamp)

Indexes:
- username: unique
- email: unique
- role: regular index

Shop Model (Shop Collection):
Fields:
- _id: MongoDB ObjectId (auto-generated)
- seller: ObjectId reference to User (required, unique per seller)
- shopname: String (required)
- description: String (optional)
- products: Array of ObjectId references to Product model
- contact: Object with email, phonenumber
- shopaddress: Object with street, city, postalcode, country
- buyingaddress: Object with street, city, postalcode, country (for billing)
- isverified: String enum (pending, verified, rejected) - default: pending
- rejectionreason: String (if rejected)
- rating: Number (shop rating, 0-5)
- earnings: Number (total seller earnings)
- createdAt: Date (auto timestamp)
- updatedAt: Date (auto timestamp)

Indexes:
- seller: unique

Product Model (Product Collection):
Fields:
- _id: MongoDB ObjectId (auto-generated)
- seller: ObjectId reference to Shop (required)
- name: String (required)
- description: String (optional)
- price: Number (required, min: 0)
- category: String (optional)
- totalStock: Number (required, min: 0)
- availableStock: Number (calculated as totalStock - reservedStock)
- reservedStock: Number (stock reserved from orders)
- images: Object with:
  * main: String (URL)
  * side1: String (URL)
  * side2: String (URL)
- rating: Number (average product rating)
- reviews: Array of ObjectId references to Review model
- status: String enum (active, inactive, discontinued) - default: active
- createdAt: Date (auto timestamp)
- updatedAt: Date (auto timestamp)

Indexes:
- seller: regular
- category: regular
- status: regular

Order Model (Order Collection):
Fields:
- _id: MongoDB ObjectId (auto-generated)
- user: ObjectId reference to User (required, buyer)
- seller: ObjectId reference to Shop (required, seller)
- items: Array of objects with:
  * product: ObjectId reference to Product (required)
  * quantity: Number (required, min: 1)
  * price: Number (price at purchase time)
- shippingAddress: Object with street, city, postalcode, country, phonenumber
- status: String enum (pending, accepted, rejected, shipped, delivered, cancelled)
- sellerStatus: String enum (pending, accepted, rejected, completed)
- totalAmount: Number (total order price)
- paymentStatus: String (pending, paid, failed, refunded)
- payment: Object reference to Payment model
- shipping: Object with:
  * trackingNumber: String
  * status: String (pending, in_transit, delivered)
  * estimatedDelivery: Date
  * deliveredAt: Date
- createdAt: Date (auto timestamp)
- updatedAt: Date (auto timestamp)

Indexes:
- user: regular
- seller: regular
- status: regular
- paymentStatus: regular

Review Model (Review Collection):
Fields:
- _id: MongoDB ObjectId (auto-generated)
- product: ObjectId reference to Product (required)
- user: ObjectId reference to User (required)
- order: ObjectId reference to Order (proof of purchase)
- rating: Number (required, 1-5)
- title: String (required)
- comment: String (required)
- isVerifiedPurchase: Boolean (true if order completed)
- helpful: Number (count of helpful votes)
- createdAt: Date (auto timestamp)
- updatedAt: Date (auto timestamp)

Indexes:
- product: regular
- user: regular

Payment Model (Payment Collection):
Fields:
- _id: MongoDB ObjectId (auto-generated)
- orderId: ObjectId reference to Order (required)
- amount: Number (total amount, required)
- platformFee: Number (10% platform commission)
- sellerAmount: Number (amount seller receives)
- status: String enum (pending, paid, failed, refunded)
- paymentMethod: String enum (card, bank_transfer, wallet)
- transactionId: String (from payment gateway)
- checkoutData: Object with cardName, cardNumber (masked), expiryDate
- createdAt: Date (auto timestamp)
- paidAt: Date (when payment completed)
- distributedToSeller: Boolean (payment sent to seller)
- distributedAt: Date (when distributed to seller)

Favourite Model (Favourite Collection):
Fields:
- _id: MongoDB ObjectId (auto-generated)
- user: ObjectId reference to User (required, unique)
- products: Array of ObjectId references to Product model
- createdAt: Date (auto timestamp)
- updatedAt: Date (auto timestamp)

Indexes:
- user: unique

RELATIONSHIPS:
- User --(1:M)--> Shop (one user = one seller shop)
- User --(1:M)--> Order (one user = multiple orders)
- Shop --(1:M)--> Product (one shop = multiple products)
- Shop --(1:M)--> Order (one shop = multiple orders)
- Product --(1:M)--> Review (one product = multiple reviews)
- User --(1:M)--> Review (one user = multiple reviews)
- Order --(1:1)--> Payment (one order = one payment record)
- User --(1:1)--> Favourite (one user = one favorite list)

SECTION 6: CORE FEATURES & FUNCTIONALITY
================================================================================

FEATURE 1: USER AUTHENTICATION & ACCOUNT MANAGEMENT
Location: backend/src/controller/auth.controller.js, routes/auth.routes.js

Features:
1. User Registration (Sign Up)
   - Email and username uniqueness validation
   - Password hashing with bcryptjs (10 salt rounds)
   - OTP generation (6-digit random code)
   - OTP validity: 10 minutes
   - Email verification with Nodemailer
   - JWT token generation (expires in 15 minutes for unverified users)
   - Error handling for duplicate accounts

2. Email Verification
   - OTP sent to registered email
   - Endpoint: POST /api/auth/verify-otp
   - OTP validation with expiry check
   - Max 5 OTP attempt limit
   - User marked as verified after successful OTP entry
   - JWT token updated with verification status

3. User Login
   - Email and password required
   - Password validation with bcryptjs
   - JWT token generation (expires in 7 days)
   - Token stored in httpOnly cookie + can be sent in Authorization header
   - Error handling for invalid credentials

4. Logout
   - Token blacklisting via tokenBlacklist service
   - Prevents token reuse after logout
   - Clears httpOnly cookie

5. Set User Role
   - After registration, user can set role: user or seller
   - Endpoint: POST /api/auth/set-role
   - Role update persists in database

Email Verification Implementation:
- Gmail SMTP configuration via Nodemailer
- OTP sent in formatted HTML email with 10-minute validity
- Subject: "Email Verification - ShopFlow"
- Includes username and clear instructions

FEATURE 2: SELLER SHOP MANAGEMENT
Location: backend/src/controller/seller.controller.js, routes/seller.routes.js

Features:
1. Create Shop
   - Endpoint: POST /api/seller/shop
   - Input: shopname, description, email, phonenumber, shopaddress, buyingaddress
   - Auto-set verification status: "pending" (awaiting admin approval)
   - Only one shop per seller
   - Trigger: Admin notification when new shop created

2. Get Shop Details
   - Endpoint: GET /api/seller/shop
   - Returns full shop profile with products, ratings, earnings
   - Requires seller authentication

3. Update Shop
   - Endpoint: PUT /api/seller/shop
   - Update any shop field
   - Requires seller authentication

Admin Shop Verification:
- Endpoint: POST /api/admin/shops/{shopId}/verify
- Verification status: pending → verified or rejected
- Rejection reason tracking
- Seller cannot add products until shop verified

FEATURE 3: PRODUCT MANAGEMENT
Location: backend/src/controller/product.controller.js, routes/product.routes.js

Features:
1. Add Product (Seller Only)
   - Endpoint: POST /api/seller/products
   - Input: name, description, price, category, totalStock, images
   - Images uploaded to ImageKit (main, side1, side2 views)
   - Auto calculation: availableStock = totalStock initially
   - Requires: Shop must be verified
   - Product added to shop's product array

2. Update Product
   - Endpoint: PUT /api/seller/products/{productId}
   - Update product details, price, stock, images
   - Stock must be recalculated after updates

3. Delete Product
   - Endpoint: DELETE /api/seller/products/{productId}
   - Soft delete via status: "discontinued"
   - Prevents order conflicts

4. Get Seller's Products
   - Endpoint: GET /api/seller/products
   - Pagination support
   - Filter by status
   - Returns all products for seller's shop

5. Get Public Products (No Auth)
   - Endpoint: GET /api/product
   - Public browsing of all active products
   - Search functionality
   - Filter by category, price range, rating
   - Pagination

Stock Management:
- totalStock: Total inventory count
- availableStock: Quantity available for purchase (totalStock - reservedStock)
- reservedStock: Stock reserved by pending orders
- Auto-update on order creation/cancellation

Product Images:
- Uploaded to ImageKit CDN
- Three image types: main, side1, side2 (for different angles)
- Automatic folder creation (/product) in ImageKit
- CDN URLs stored in database

FEATURE 4: ORDER MANAGEMENT
Location: backend/src/controller/order.controller.js, routes/order.routes.js

Order Lifecycle:
┌─────────────┐
│   pending   │ (User creates order from cart)
└──────┬──────┘
       │ (Seller accepts/rejects)
       ▼
┌─────────────────────┐
│ accepted/rejected   │
└──────┬──────────────┘
       │ (Payment processed)
       ▼
┌──────────────┐
│    paid      │ (Checkout → Payment)
└──────┬───────┘
       │ (Seller ships order)
       ▼
┌──────────────┐
│   shipped    │ (TCS shipment created)
└──────┬───────┘
       │ (Auto-delivery after timeout)
       ▼
┌──────────────┐
│  delivered   │ (Payment distributed to seller)
└──────────────┘

1. Create Order
   - Endpoint: POST /api/orders
   - Input: items (array of {product, quantity}), shippingAddress
   - Auto calculation: totalAmount from product prices
   - Initial status: pending
   - Stock reservation: availableStock decreases, reservedStock increases

2. Seller Accept/Reject Order
   - Endpoint: POST /api/seller/orders/{orderId}/accept
   - Endpoint: POST /api/seller/orders/{orderId}/reject
   - Seller notification via Socket.io
   - Updates sellerStatus and order status

3. Checkout & Payment
   - Endpoint: POST /api/orders/{orderId}/checkout
   - Creates Payment record
   - Calculates platform fee (10%)
   - Status: pending_payment
   - Endpoint: POST /api/payment/process
   - Validates payment data
   - Updates payment status: paid
   - Order status: payment_completed

4. Shipping & Tracking
   - Endpoint: POST /api/orders/ship/{orderId}
   - Requires: Payment completed
   - Calls TCS service (simulated)
   - Generates tracking number
   - Estimated delivery: 1 minute (testing), 5 days (production)
   - Order status: shipped
   - Endpoint: GET /api/orders/tracking/{trackingNumber}
   - Returns tracking status, location, estimated delivery
   - Auto-delivery after timeout via Agenda scheduler

5. Order Tracking
   - Real-time updates via Socket.io notifications
   - Status changes pushed to user

6. Invoice Generation
   - Endpoint: GET /api/orders/invoice/{orderId}
   - Generates PDF invoice with order details
   - Available only for completed orders

Seller Order Management:
- Endpoint: GET /api/seller/orders
- Pagination support
- Filter by: status, sellerStatus
- Statuses: pending, accepted, rejected, shipped, delivered, cancelled
- Order completion: POST /api/seller/orders/{orderId}/complete
- Order archival: DELETE /api/seller/orders/{orderId}

FEATURE 5: PAYMENT PROCESSING
Location: backend/src/services/payment.service.js, routes/order.routes.js

Payment Flow:
1. User creates order
2. User initiates checkout
3. Payment record created with platform fee calculation
4. User submits payment details (dummy validation)
5. Payment marked as paid
6. Order status updated to shipped-ready
7. On delivery completion, payment distributed to seller

Payment Details:
- Platform Fee: 10% of order amount
- Seller Amount: Total - Platform Fee
- Payment Methods: card, bank_transfer, wallet
- Payment Status: pending, paid, failed, refunded
- Security: Card numbers not stored, CVV never stored
- Masked card storage in checkoutData

Platform Commission Structure:
- 10% platform fee on all transactions
- Automatically deducted from seller earnings
- Tracked in Payment model
- Distributed to seller account on order delivery

Dummy Payment Processing:
- Validates card number format (simulated)
- Validates expiry date format
- Auto-approves all payments (for testing)
- Generates fake transaction ID
- Does NOT charge real payment (testing only)
- In production: Replace with Stripe/PayPal integration

FEATURE 6: PRODUCT REVIEWS & RATINGS
Location: backend/src/controller/review.controller.js, routes/review.routes.js

Features:
1. Add Review (Verified Purchase Only)
   - Endpoint: POST /api/reviews
   - Input: productId, rating (1-5), title, comment
   - Verification: Order must be completed and delivered
   - Rating: Required, 1-5 stars
   - Title & Comment: Required text fields

SECTION 8: AUTHENTICATION & SECURITY
================================================================================

AUTHENTICATION MECHANISM:

JWT (JSON Web Tokens):
- Token Creation: signUp/login endpoint
- Token Format: Bearer token
- Token Storage: 
  * httpOnly cookie (secure)
  * localStorage (frontend)
- Token Expiry: 7 days for regular users, 15 minutes for unverified users
- Secret Key: process.env.SECRET_KEY
- Algorithm: HS256 (HMAC SHA-256)
- Token Payload: {id, role, verified, iat, exp}

Token Verification:
- Checked in auth.middleware.js for all protected routes
- Extracted from: Authorization header (Bearer token) or cookies
- Token blacklist checked on every request (after logout)
- Invalid/expired tokens return 401 Unauthorized

Role-Based Authorization:
- Middleware: roleMiddleware(requiredRoles)
- Roles: user, seller, admin
- Applied per route: /api/seller/* requires seller role
- Role check: req.user.role compared against required role
- Unauthorized access returns 403 Forbidden

Password Security:
- Algorithm: bcryptjs
- Hash rounds: 10 (strength = 2^10 iterations)
- Password minimum length: 6 characters
- Required components: uppercase, lowercase, numbers
- Validation: Enforced in auth.validation.js
- Never returned in API responses
- Comparison: bcryptjs.compare() for login

Email Verification:
- OTP Method: 6-digit random code
- Expiry: 10 minutes after generation
- Delivery: Nodemailer via Gmail SMTP
- Max attempts: 5 before rate limit
- User marked as verified only after OTP validation
- Email-based verification prevents fake accounts

Token Blacklist System:
- On logout: Token added to blacklist
- Storage: In-memory Set (TODO: Move to Redis for production)
- Checked on every request via isTokenBlacklisted()
- Prevents token reuse after logout
- Limitation: In-memory storage lost on server restart

SECURITY FEATURES:

1. Password Hashing
   - Method: bcryptjs with 10 salt rounds
   - Salted hashing prevents rainbow table attacks
   - Password never stored in plain text

2. Data Validation
   - Input sanitization via express-validator
   - Field length validation
   - Email format validation (regex)
   - Phone number validation (10-15 digits)
   - Type checking for numeric fields

3. CORS Configuration
   - Origin: '*' (allows all for testing)
   - Credentials: enabled
   - Allowed methods: GET, POST, PUT, DELETE, PATCH, OPTIONS
   - Allowed headers: Content-Type, Authorization

4. Helmet Middleware
   - Adds security headers to responses
   - Prevents common web vulnerabilities
   - Configured in app.js

5. Cookie Security
   - httpOnly: true (prevents XSS attacks)
   - Secure: true (HTTPS only in production)
   - SameSite: strict (CSRF prevention)

6. MongoDB Injection Prevention
   - Mongoose schema validation
   - Type casting prevents injection
   - Input sanitization via validators

7. Rate Limiting (TODO)
   - Not currently implemented
   - Recommended: express-rate-limit
   - Prevent brute force attacks on login/register

8. Image Upload Security
   - File type validation
   - Size limits via Multer
   - Upload to external CDN (ImageKit) not local server
   - Prevents server storage abuse

PRODUCTION SECURITY RECOMMENDATIONS:

1. Environment Variables
   - Use .env file (never commit)
   - Store sensitive keys: SECRET_KEY, database URI, email password
   - Rotate keys periodically

2. HTTPS
   - Enable in production (secure: true in cookies)
   - Use SSL certificates

3. Database Security
   - Use MongoDB authentication
   - Restrict network access
   - Enable encryption at rest
   - Regular backups

4. API Security
   - Implement rate limiting
   - API key authentication for third-party APIs
   - Request validation stricter rules
   - SQL/NoSQL injection prevention (already done)

5. Token Management
   - Move token blacklist to Redis
   - Reduce token expiry to 1 hour + refresh tokens
   - Implement token refresh flow

6. Logging & Monitoring
   - Log all authentication events
   - Monitor for suspicious activity
   - Alert on multiple failed login attempts

7. Payment Security
   - In production: Use Stripe or PayPal
   - PCI DSS compliance
   - Never store full card numbers
   - CVV never stored

8. Infrastructure
   - Use HTTPS/TLS
   - Enable firewall rules
   - Regular security audits
   - Keep dependencies updated

SECTION 10: VALIDATION & ERROR HANDLING
================================================================================

BACKEND VALIDATION:

Authentication Validation (auth.validation.js):
- Username: Min 3 chars, max 30 chars, alphanumeric + underscore
- Email: Valid email format (regex), unique in database
- Password: Min 6 chars, must include uppercase, lowercase, number
- OTP: Must be 6 digits
- Role: Must be 'user' or 'seller'

User Validation (user.validation.js):
- Phone number: 10-15 digits
- Date of birth: Valid date format
- Address fields: Required for orders

Product Validation (product.validation.js):
- Name: Required, string
- Price: Required, must be > 0
- Category: Optional, string
- TotalStock: Required, must be >= 0
- Description: Optional, max 1000 chars

Order Validation (sellerorder.validation.js):
- Items array: Must contain at least 1 item
- Shipping address: All fields required (street, city, postal, country)
- Product ID: Must exist in database
- Quantity: Must be > 0 and <= availableStock

Review Validation (review.validation.js):
- Rating: Required, must be 1-5
- Title: Required, min 5 chars, max 100 chars
- Comment: Required, min 10 chars, max 500 chars
- Product ID: Must exist
- User: Must be verified purchaser

Shop Validation (seller.validation.js):
- Shop name: Required, min 3 chars
- Description: Optional
- Contact email: Valid email format
- Phone number: 10-15 digits
- Addresses: All required (street, city, postal, country)

Admin Validation (admin.validation.js):
- Settings update: Validate fee percentages (0-100)
- User suspension: Check user exists
- Shop rejection: Reason required

ERROR HANDLING:

Backend Error Responses:

1. Validation Errors (400 Bad Request)
   - Response format: {success: false, errors: [{field, message}], message}
   - Example:
     {
       "success": false,
       "message": "Validation failed",
       "errors": [
         {"field": "email", "message": "Invalid email format"},
         {"field": "password", "message": "Password must be at least 6 characters"}
       ]
     }

2. Authentication Errors (401 Unauthorized)
   - No token provided
   - Token expired
   - Token invalid
   - Token blacklisted
   - Response: {success: false, message: "Authentication error message"}

3. Authorization Errors (403 Forbidden)
   - User lacks required role
   - Seller lacks verified shop status
   - Response: {success: false, message: "Access denied. Required role(s): seller"}

4. Not Found Errors (404 Not Found)
   - User not found
   - Product not found
   - Order not found
   - Shop not found
   - Response: {success: false, message: "Resource not found"}

5. Conflict Errors (409 Conflict)
   - Email/username already exists
   - Duplicate shop creation
   - Response: {success: false, message: "Resource already exists"}

6. Server Errors (500 Internal Server Error)
   - Database connection errors
   - Unexpected exceptions
   - Response: {success: false, message: "Internal server error"}

All error responses include:
- success: false
- data: null
- message: Human-readable error message
- errors: (optional) Array of validation errors

FRONTEND ERROR HANDLING:

Toast Notifications (react-hot-toast):
- Success: Green toast for successful operations
- Error: Red toast for errors
- Warning: Yellow toast for warnings
- Info: Blue toast for info messages

Error Handling Flow:
1. API call made via Axios
2. Response interceptor checks status
3. On error: Toast notification displayed
4. Error logged to console (development)
5. User redirected if needed (login expired, etc.)

Common Frontend Errors:
- Network errors: "Unable to connect to server"
- 401 errors: "Session expired. Please login again"
- 403 errors: "You don't have permission to access this"
- 404 errors: "Resource not found"
- Validation errors: Field-level error messages
- Payment errors: "Payment failed. Please try again"

SECTION 14: JOB SCHEDULING (AGENDA)
================================================================================

AGENDA SCHEDULER:

Job Scheduling Library: Agenda
- MongoDB integration via @agendajs/mongo-backend
- Stored in MongoDB: agenda collection
- Runs on schedule defined in jobs

Initialization:
- Called at server startup
- Connects to MongoDB
- Loads defined jobs
- Starts job processing

Auto-Delivery Job:

Trigger:
- Runs every 30 seconds
- Checks all orders with status "shipped"
- Finds shipments with elapsed time > 1 minute

Logic:
1. Get all shipped orders
2. Check shipping.createdAt timestamp
3. Calculate elapsed time in minutes
4. If elapsed > 1 minute:
   - Update order status: shipped → delivered
   - Update shipping.status: in_transit → delivered
   - Set shipping.deliveredAt: current timestamp
   - Distribute payment to seller
   - Update seller earnings

Payment Distribution:
- Triggered on order delivery
- Amount: sellerAmount from Payment model (after 10% platform fee)
- Update seller.earnings
- Set payment.distributedToSeller: true
- Set payment.distributedAt: current timestamp

Graceful Shutdown:
- On SIGINT (Ctrl+C): Stop agenda scheduler
- Cancel pending jobs
- Close server connections
- Exit process cleanly

SECTION 16: DEPLOYMENT CONSIDERATIONS
================================================================================

CURRENT LIMITATIONS:

Single Instance Deployment:
- Single Node.js process
- Single MongoDB instance
- No load balancing
- Single point of failure
- Limited concurrent users: 5,000-10,000

No Caching Layer:
- No Redis caching
- Every request hits MongoDB
- No session caching
- Slower response times for repeat queries

No Content Delivery Network (CDN):
- Static assets served from server
- Images served from ImageKit (good)
- No geographic distribution

No Rate Limiting:
- No request throttling
- Vulnerable to DoS attacks
- Brute force attacks possible

Token Blacklist In-Memory:
- Lost on server restart
- Doesn't scale across servers
- Should use Redis

PRODUCTION DEPLOYMENT STEPS:

1. Environment Setup:
   - Create .env file with production values
   - Use secure password management (HashiCorp Vault, AWS Secrets Manager)
   - Set NODE_ENV=production

2. Database:
   - Use MongoDB Atlas (cloud) or managed MongoDB
   - Enable authentication
   - Configure firewall rules
   - Enable encryption at rest
   - Set up automated backups
   - Configure replication

3. Backend Deployment:
   - Use PM2 or Docker for process management
   - Enable clustering: pm2 start server.js -i max
   - Use load balancer (Nginx, HAProxy)
   - Set up reverse proxy
   - Enable HTTPS/SSL

4. Frontend Deployment:
   - Build: npm run build
   - Deploy to CDN (Vercel, Netlify, AWS S3 + CloudFront)
   - Set VITE_API_BASE_URL to production API URL
   - Enable caching headers

5. Caching:
   - Set up Redis instance
   - Cache: user sessions, product listings, analytics
   - Use redis-session-store for sessions
   - Implement cache invalidation strategy

6. Monitoring:
   - Set up error tracking (Sentry)
   - Log aggregation (ELK Stack, DataDog)
   - Performance monitoring
   - Uptime monitoring

7. Security:
   - Enable HTTPS/TLS
   - Set up firewall rules
   - Regular security audits
   - Dependency scanning
   - Keep dependencies updated

DOCKER DEPLOYMENT:

Backend Dockerfile:
```
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 5000
CMD ["node", "server.js"]
```

Docker Compose:
```
version: '3'
services:
  api:
    build: ./backend
    ports:
      - "5000:5000"
    environment:
      DATABASE_URI: mongodb://mongo:27017/ecommerce
      NODE_ENV: production
    depends_on:
      - mongo
  mongo:
    image: mongo:latest
    ports:
      - "27017:27017"
    volumes:
      - mongo-data:/data/db
volumes:
  mongo-data:
```

SCALING STRATEGY:

Vertical Scaling:
- Increase server resources (CPU, RAM)
- Larger database instance
- Not recommended past 20,000 users

Horizontal Scaling:
- Multiple Node.js instances behind load balancer
- Database replication
- Redis cluster for caching
- Separate read replicas for analytics

Database Optimization:
- Indexing on frequently queried fields
- Query optimization
- Pagination to reduce data transfer
- Aggregation pipelines for analytics
